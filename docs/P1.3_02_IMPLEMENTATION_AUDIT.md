## 1. Parecer Executivo

Atuando como auditor independente de engenharia de software especializado em Ruby, segurança de parsers, integridade lexical de dados e testes adversariais, o Antigravity realizou a auditoria completa da implementação técnica e sintética da **P1.3-02 — Identidade e Metadados Markdown**, entregue pelo Codex na branch `p1.3-metadata`.

A inspeção direta do código-fonte, a conferência contratual normativa contra C-01–C-11 com os ajustes R1/R2/R3 reconciliados, a análise do pipeline de segurança no Psych/libyaml e a reprodução integral das suítes de testes isoladas, integradas, SQL e de medição experimental confirmam que:

1. **Aderência Normativa Estrita:** As regras consolidadas C-01 a C-11 e os refinamentos R1 (gate positivo de rascunhos sem autorização de escrita), R2 (aviso `date_order_anomaly` para datas invertidas válidas) e R3 (preservação literal de tags duplicadas com aviso `duplicate_tag`) foram rigorosamente implementados.
2. **Segurança e Blindagem contra DoS:** O parser YAML restrito (`Vault::Metadata::YamlParser` e `GuardedTreeBuilder`) bloqueia tags customizadas, aliases, âncoras, diretivas, múltiplos documentos e merges antes da expansão de objetos Ruby. A detecção de chaves duplicadas é feita de forma iterativa diretamente sobre a AST antes de qualquer conversão para Hash.
3. **Fidelidade Lexical e Preservação de Bytes:** O enquadramento em `Vault::Document` preserva byte a byte o envelope bruto original (`raw_header` com BOM, quebras LF/CRLF mistas, comentários e delimitadores `---`), enquanto o `Vault::Serializer` opera estritamente em memória recusando qualquer round-trip destrutivo (`update_properties`) sobre arquivos existentes.
4. **Agregação Coletiva e Honestidade de Escala:** O `Vault::Metadata::IdentitySet` agrupa claims puras sem reter corpos em memória, exige observação completa para emitir `unique_in_observation`, rebaixa para `unverified` em caso de inventários parciais/estouro de limites e marca todas as cópias com o mesmo ID como `conflicting`, impedindo qualquer escolha arbitrária ou first-come.
5. **Isolamento e Ausência de Regressões:** P1.3-01 e P1.2 permanecem 100% intactas. Não há operações de escrita no filesystem do Vault, nenhuma rota/controller/view foi criada, nenhum banco de dados operacional foi tocado e o isolamento de processo confirmou ausência de ActiveRecord ou SQLite3 na suíte pura do Vault.

## 3. Conformidade com as Regras de Reconciliação R1, R2 e R3

### R1 — Rascunhos e Identidade (`Serializer#replace_body`)
- **Implementação Auditada:**
  ```ruby
  allowed = document.kind == :note && document.read_state == :complete && document.valid_metadata? &&
    document.parse_status == :valid && [ :unverified, :unique_in_observation ].include?(document.identity_status)
  return failure(:unsupported_edit) unless allowed
  ```
- **Conformidade:** A lista de estados permitidos é estritamente positiva (`:unverified` e `:unique_in_observation`). Qualquer documento com `identity_status: :conflicting`, `:not_applicable`, desconhecido, ou com leitura/parsing incompleto é recusado com `:unsupported_edit`.
- **Garantia de Não-Gravação:** O `Serializer::Result` gerado é um `Data.define` imutável em memória. O serviço não possui métodos de filesystem, descritores de arquivo ou dependência de escrita.

### R2 — Ordem Temporal de Datas (`date_order_anomaly`)
- **Implementação Auditada:**
  ```ruby
  def dates!(fields)
    if fields["created_at"] && fields["updated_at"] && instant!(fields["updated_at"], "updated_at") < instant!(fields["created_at"], "created_at")
      @diagnostics.add(:date_order_anomaly)
    end
  end
  ```
- **Conformidade:** Quando ambas as datas são válidas individualmente, a inversão temporal adiciona o aviso estruturado `date_order_anomaly` com severidade `:warning`, mantendo o documento como `parse_status: :valid`. Os valores literais de string, timezone e precisão fracionária são 100% preservados no hash `fields`. Formatos inválidos (ex.: datas sem timezone, formato inválido, `-00:00`) continuam gerando erro invalidante `invalid_date`.

### R3 — Preservação de Tags Duplicadas (`duplicate_tag`)
- **Implementação Auditada:**
  ```ruby
  when "tags", "project_ids", "task_ids"
    list = list!(node, name, max: @limits[name == "tags" ? :tags : :references]).map do |item|
      name == "tags" ? text!(item, name, max: @limits[:tag_bytes], limit_code: :tag_limit) : id!(item, name)
    end
    if list.uniq.size != list.size
      name == "tags" ? @diagnostics.add(:duplicate_tag, field: name) : fail!(:duplicate_value, field: name)
    end
    list
  ```
- **Conformidade:** Para `tags`, a lista integral com todas as repetições é preservada na ordem original (sem trim, sem casefold, sem normalização Unicode), emitindo o aviso `:duplicate_tag`. Todas as ocorrências contam nos limites (`limits[:tags]`, `limits[:nodes]`). Já para `project_ids` e `task_ids`, duplicatas continuam falhando imediatamente com o erro invalidante `duplicate_value`. Chaves YAML duplicadas e bindings duplicados continuam estritamente invalidantes.

## 4. Análise de Segurança do Parser YAML

A auditoria inspecionou as defesas e camadas de contenção contra ataques e comportamentos anômalos em [yaml_parser.rb](file:///home/goecking/Projects/Accio-HUB/rails/app/services/vault/metadata/yaml_parser.rb):

1. **Pré-checagens de Bytes e Linhas:** Antes de acionar o Psych, `Guard#precheck!` valida o tamanho total do cabeçalho ($\le 64$ KiB), o número de quebras de linha ($\le 2.048$ LFs), a validade do encoding UTF-8 (rejeitando bytes malformados sem substituição silenciosa) e a ausência de terminações isoladas de CR (`\r(?!\n)`).
2. **Defesa Antecipada no Handler (`GuardedTreeBuilder`):**
   - Intercepta `alias`: aborta imediatamente com `:forbidden_alias`, impedindo o parsing de âncoras circulares ou bombas de descompressão (Billion Laughs).
   - Intercepta `anchor`: recusa qualquer nó com âncora (`:forbidden_anchor`).
   - Intercepta `tag`: recusa terminantemente tags explícitas (`:forbidden_tag`), incluindo tags Core como `!!str`, `!!map`, `!!seq` ou tags Ruby arbitrárias (`!ruby/object`).
   - Intercepta `start_document`: recusa diretivas (`%YAML`, `%TAG`) e múltiplos documentos (`:multiple_documents`).
   - Contadores cooperativos: nós contados e limitados a 4.096; profundidade limitada a 16 containers; escalares limitados a 8.192 bytes; elementos de mapping limitados a 256 pares e sequence a 512 itens.
3. **Detecção Rigorosa de Chaves Duplicadas via AST:**
   - Após a construção da árvore protegida, `inspect_tree!` percorre recursivamente os nós de mapeamento utilizando uma pilha iterativa (`stack`).
   - Em cada `Psych::Nodes::Mapping`, os filhos são inspecionados em pares `children.each_slice(2)`. Chaves duplicadas são detectadas comparando os valores escalares em um dicionário local (`mapping.key?(name)`), levantando `fail!(:duplicate_key)`. Essa verificação ocorre **antes** de qualquer conversão para objetos de aplicação ou invocação de bibliotecas de alto nível.
4. **Isolamento de Tipos e Escalares:**
   - `Metadata.scalar_type` implementa resolução estrita do Core Schema YAML 1.2.2 sem carregar bibliotecas ou instanciar objetos Ruby dinâmicos.
   - Escalares plain são restritos: strings que se assemelham a números (`42`, `0xFF`), booleanos (`true`, `false`) ou nulos (`null`, `~`) são categorizados lexicalmente, impedindo coerções implícitas perigosas em campos como `id`.

## 5. Integridade do Document e Serializer

A preservação lexical e a ausência de caminhos destrutivos foram verificadas em [document.rb](file:///home/goecking/Projects/Accio-HUB/rails/app/services/vault/document.rb) e [serializer.rb](file:///home/goecking/Projects/Accio-HUB/rails/app/services/vault/serializer.rb):

1. **Reconstituição Exata de Bytes:**
   - O método `Document#set_ranges!` mapeia precisamente os offsets de BOM UTF-8 (3 bytes), YAML e corpo Markdown.
   - `Document#raw_header` captura integralmente o prefixo pré-corpo, preservando comentários, espaçamento, ordem de chaves e quebras de linha (incluindo CRLF e mistos).
   - O teste comprovou que `doc.raw_header + doc.raw_body == doc.raw_bytes` de forma invariante.
2. **Tratamento de Caracteres Especiais Unicode (NEL, LS, PS):**
   - Foi comprovado que a biblioteca nativa `libyaml` converte quebras NEL (`U+0085`) em espaços durante o desdobramento de linhas em strings com aspas.
   - O `Serializer#quoted` trata especificamente essa peculiaridade escapando explicitamente `\u0085`, `\u2028` e `\u2029`.
   - Em `Serializer#compose_new`, a emissão do novo frontmatter é seguida de reparse imediato com `Document.from_bytes` e validação de equivalência semântica estrita (`equivalent?`). Se houver qualquer discrepância entre os campos pretendidos e os campos reparseados, a composição é abortada com `:unsupported_edit`.
3. **Ausência de Efeitos no Filesystem:**
   - O `Serializer` devolve instâncias de `Serializer::Result` contendo bytes e diagnósticos. Nenhum descritor de arquivo é aberto, nenhum método de I/O é invocado e nenhuma capacidade de escrita é transferida para as camadas superiores.

## 6. Identidade Coletiva e Honestidade de Escala

A implementação de agregação em [identity_set.rb](file:///home/goecking/Projects/Accio-HUB/rails/app/services/vault/metadata/identity_set.rb) foi examinada contra os requisitos de honestidade de lote e concorrência:

1. **Isolamento de Memória (Claims Puras):**
   - O `IdentitySet` não retém instâncias de `Vault::Document` nem seus `raw_bytes` ou corpos Markdown. Ele armazena descrições compactas contendo apenas caminhos, hashes, kinds e claims (`claimed_id`).
   - O teto de memória de texto retido ($\le 8$ MiB) e limite de entradas ($\le 10.000$) impedem esgotamento de memória em grandes bibliotecas.
2. **Independência de Ordem e Tratamento de Conflitos:**
   - Caso dois documentos no lote sob observação declarem o mesmo ID no mesmo namespace (note vs folder), **todos** os documentos colidentes são marcados como `identity_status: :conflicting` e `classification: :identity_conflict`.
   - Nenhuma política de "primeiro a chegar" (first-come) ou eleição arbitrária por timestamp/mtime é adotada. A ordem dos itens no array de entrada é irrelevante para o resultado final.
3. **Lotes Parciais e Incompletos:**
   - Se o lote for interrompido por estouro de orçamento (`budget.check!`), timeout, leitura negada ou limite de entradas, o status de cobertura (`@coverage`) torna-se falso.
   - Documentos localmente válidos no lote incompleto recebem obrigatoriamente `identity_status: :unverified` acompanhado do diagnóstico `identity_incomplete`. Nenhum documento é promovido a `unique_in_observation` em lote parcial.
4. **Revogação de Unicidade em Exceções Tardias:**
   - O método `revoke_uniqueness!` garante que, caso ocorra timeout ou estouro de recursos durante a etapa de finalização do lote, qualquer status `unique_in_observation` preliminarmente atribuído é imediatamente rebaixado para `unverified`.
