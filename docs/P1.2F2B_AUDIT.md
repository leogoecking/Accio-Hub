## 3. Auditoria F2B-01 — Intenção Malformada de Projeto

### 3.1 Causa Raiz Confirmada
Durante a exploração adversarial da F2b, identificou-se que requisições enviando um objeto JSON estruturado no campo `intent` (e.g. `{"intent": {"forged": true}, "project": {"name": "..."}}`) causavam uma exceção não tratada `NoMethodError (undefined method 'valid_encoding?' for ActionController::Parameters)` dentro de `ActiveSupport::MessageVerifier#verified`.  
O `MessageVerifier` do Rails assume que a entrada para decodificação e verificação de assinatura é estritamente uma `String`. Ao receber uma instância de `ActionController::Parameters`, ocorria um estouro interno de tipo antes de qualquer validação de assinatura, resultando em **HTTP 500 Internal Server Error** com vazamento potencial de detalhes da pilha no modo development.

### 3.2 Correção Aplicada e Eficácia da Guarda
A correção aplicada pelo Codex em [`rails/app/services/project_commands.rb`](file:///home/goecking/Projects/Accio-HUB/rails/app/services/project_commands.rb#L15) consiste exclusivamente em:

```ruby
claim = verifier.verified(intent, purpose: "project-create") if intent.is_a?(String)
```

**Análise técnica da auditoria:**
- A guarda `if intent.is_a?(String)` impede que qualquer tipo não escalar ou incompatível atinja o `MessageVerifier`.
- Caso `intent` não seja uma `String`, `claim` permanece `nil`.
- Na linha seguinte, a verificação `unless claim.is_a?(Hash) && ...` avalia como falsa e dispara a exceção de domínio `raise InvalidIntent, "Intenção inválida. Abra um novo formulário; seus campos foram mantidos."`.
- O controller captura `InvalidIntent` e emite uma resposta **HTTP 422 Unprocessable Content** padronizada com `{ "error": "invalid_project", "message": "Intenção inválida..." }`.
- **Não há uso de `rescue Exception` ou mascaramento genérico:** a correção atua pontualmente na validação do tipo esperado, mantendo intactos o tratamento de erros do controller, CSRF, autenticação e idempotência.

## 5. Auditoria Transversal de Segurança

### 5.1 Autenticação e Gestão de Sessões
- **Acesso Desautenticado:** Rotas privadas de HTML redirecionam imediatamente para `/session/new`. Endpoints de API retornam HTTP 401 Unauthorized, mesmo quando a requisição carrega um token CSRF válido emitido para sessão anônima.
- **Expiração:** Sessões com `expires_at` no passado são rejeitadas em todas as rotas protegidas.
- **Logout e Revogação:** O endpoint `DELETE /session` remove o registro em `AuthSession`. Reenvios do cookie assinado legado após o logout são recusados com 401/redirect.
- **Admin Reset:** O utilitário administrativo (`bin/rails admin:reset`) opera estritamente via terminal interativo (PTY/stdin), revoga todas as sessões ativas e expiradas, e não possui nenhuma rota HTTP exposta.
- **Ausência de Cadastro Público:** Confirmada a inexistência de rotas para criação pública de contas.

### 5.2 CSRF e Proteção de Comandos
- **CSRF Efetivo:** Os testes executam com `ActionController::Base.allow_forgery_protection = true`. Requisições POST/PATCH/DELETE sem token, com token incorreto ou provenientes de origem cruzada (`HTTP_ORIGIN = "https://evil.test"`) são sumariamente recusadas com HTTP 422 em todas as 16 operações testadas, sem causar mutação nos modelos.
- **Intenções Assinadas:** Intenções forjadas, com assinatura violada, pertencentes a outro usuário ou destinadas a outra entidade (e.g. intenção de projeto usada em tarefas) recebem HTTP 422 controlado.
- **Strong Parameters:** Tentativas de injeção de atributos internos restritos (`user_id`, `uid`, `completed_at`, `lock_version`, `project_id`) são descartadas pelos parâmetros fortes, mantendo os valores originais intactos.

### 5.3 Concorrência, Conflito e Contenção SQLite Real
- **Locking Otimista (HTTP 409):** Requisições concorrentes de edição ou comandos com versões desatualizadas de agregados de preferência, projetos, tarefas ou foco recebem HTTP 409 Conflict de forma consistente.
- **Contenção Real SQLite (HTTP 503):** Processos simultâneos executando `BEGIN IMMEDIATE` provocam contenção de escrita real na camada de conexão SQLite, respondida pelo Rails como **HTTP 503 Service Unavailable** com mensagem de recuperação para o cliente. A liberação do lock e a reabertura do processo confirmam ausência total de gravações parciais (rollback atômico).
- **Unicidade do Foco Global:** O índice parcial SQL `one_global_focus` garante a existência de no máximo uma sessão nos estados ativos (`ready`, `running`, `paused`, `awaiting_confirmation`). Tentativas simultâneas de ocupação por processos concorrentes resultam em 1 vencedor (HTTP 200) e 1 conflito rejeitado (HTTP 409), sem duplicar o slot global.
- **Imutabilidade de Recibos:** Comandos de foco registrados em `focus_commands` possuem gatilhos SQL que impedem qualquer operação de `UPDATE` ou `DELETE`, mesmo via SQL direto.
