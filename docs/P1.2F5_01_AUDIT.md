## 6. Causa Raiz Confirmada

**Veredito: CAUSA RAIZ CONFIRMADA.**

### Explicação Técnica

Em [`rails/config/environments/development.rb`](file:///home/goecking/Projects/Accio-HUB/rails/config/environments/development.rb#L41), encontra-se a seguinte diretiva do Rails 8:

```ruby
# Annotate rendered view with file names.
config.action_view.annotate_rendered_view_with_filenames = true

# Uncomment if you wish to allow Action Cable access from any origin.
# config.action_cable.disable_request_forgery_protection = true

# Raise error when a before_action's only/except options reference missing actions.
config.action_controller.raise_on_missing_callback_actions = true

# Tag queries with execution context
config.active_record.query_log_tags_enabled = true
```

1. Quando `config.active_record.query_log_tags_enabled = true`, o adaptador do ActiveRecord intercepta todas as instruções SQL executadas e anexa tags de comentário no formato SQL standard `/*chave='valor'*/`. A configuração de tags do projeto define `application='AccioHub'`.
2. Quando o Rails executa migrações ou `db:schema:load`, ele invoca o método `add_index` do ActiveRecord, o qual emite comandos `CREATE INDEX ...`.
3. Por estar sob o ambiente `development`, o ActiveRecord anexa o comentário ` /*application='AccioHub'*/` ao final da string do `CREATE INDEX`.
4. O SQLite grava no catálogo interno `sqlite_master` a instrução DDL textual exatamente como ela foi submetida pela conexão do banco de dados.
5. Em contraste, os gatilhos (`CREATE TRIGGER`) são criados através de comandos de migração com SQL bruto (`execute <<-SQL ...`), contornando o mecanismo de anotação de índices do schema statement do ActiveRecord.
6. No ambiente `test`, `query_log_tags_enabled` não está ativo por padrão, de modo que nenhum comentário é inserido.
7. Quando a ferramenta F3b lê `sqlite_master`, ela lê o SQL persistido. A computação do SHA256 sobre a estrutura textual captura os comentários, resultando no hash divergente `b42e0bb5...`.

## 8. Análise Crítica e Adversarial das Alternativas

A auditoria comparou detalhadamente as soluções concebíveis:

### Alternativa A: Catalogação do Hash Legítimo de Development na Whitelist do Contrato

Consiste em incluir o fingerprint `b42e0bb59d064152d690856959275801ae4f1e034e291765d56bbc1874986470` no array `"schema_sha256"` de `rails/config/sqlite_backup_contract.json`.

- **Vantagens Arquiteturais:**
  - **Zero linhas de código alteradas:** o código de `SyntheticSqliteBackup#compatible!` já foi projetado na F3b para receber um array de hashes autorizados:
    ```ruby
    @contract.fetch("schema_sha256").include?(snapshot.fetch("schema_sha256"))
    ```
  - **Determinismo estrito:** não há manipulação, regex, limpeza ou normalização de strings em tempo de execução. O hash verificado é exato e imutável.
  - **Impossibilidade de mascaramento:** qualquer alteração em colunas, tabelas, triggers, chaves ou comentários resulta em um hash que não pertencerá à lista de dois hashes estritos autorizados.
- **Limitações:**
  - Se no futuro novas tags forem introduzidas no Rails, um novo hash previsível precisará ser explicitamente homologado no contrato. No contexto de um aplicativo local-first com SQLite estrito, essa explicitude é uma virtude de governança.

### Alternativa B: Normalização Estritamente Delimitada de Query Log Tags

Consiste em modificar `SqliteBackupSnapshot` ou `SyntheticSqliteBackup` para remover em memória o sufixo `" /*application='AccioHub'*/"` antes de calcular o hash.

- **Vantagens:**
  - Mantém apenas um único hash no contrato JSON.
- **Riscos e Desvantagens:**
  - **Alteração de código no motor crítico:** exige modificar código homologado na F3b.
  - **Risco de sanitização inadequada:** se implementada de forma genérica (ex: regex para remover qualquer comentário SQL `/\/\*.*?\*\//`), abre uma vulnerabilidade séria onde um atacante ou extensão externa poderia adulterar definições DDL ocultando payloads em comentários.
  - Mesmo estritamente delimitada (`delete_suffix`), introduz uma regra de mutação sintética em memória antes da auditoria criptográfica.

### Alternativa C: Desativar `query_log_tags_enabled` em `development.rb`

Consiste em comentar ou definir como `false` a diretiva `config.active_record.query_log_tags_enabled` em `rails/config/environments/development.rb`.

- **Desvantagens:**
  - Não resolve o problema para bases de dados de desenvolvimento já criadas e existentes no disco do desenvolvedor (onde os índices já foram gravados em `sqlite_master` com o comentário).
  - Reduz a capacidade de diagnóstico de logs durante o desenvolvimento interativo do Rails.

## 10. Recomendação da Menor Correção Segura

A auditoria recomenda com total clareza a adoção da **Alternativa A**:

### Justificativa Técnica

1. **Fidelidade ao Design de F3b:** O contrato `sqlite_backup_contract.json` já foi concebido estruturalmente como um array (`"schema_sha256": [ ... ]`) exatamente para catalogar fingerprints de schemas homologados da aplicação.
2. **Zero Risco de Regressão em Código:** Nenhuma alteração é necessária em arquivos `.rb`, rotas, migrações ou testes unitários de serviços.
3. **Mínima Intervenção:** Modifica exclusivamente um arquivo estático de configuração declarativa (`config/sqlite_backup_contract.json`), adicionando o segundo fingerprint legítimo e verificado.
4. **Sem Efeitos Colaterais:** Não afeta a inicialização do Rails, as query log tags de debug em development, o comportamento dos navegadores ou o banco de dados em `test`.

## 13. Riscos e Limitações

- **Risco Residual:** Caso futuras versões do Rails ou customizações alterem as tags de logging do ActiveRecord adicionando chaves dinâmicas ao DDL (ex.: timestamps), o hash DDL em development mudaria novamente. Contudo, em operações DDL executadas por migrações em lote, o ActiveRecord utiliza apenas tags de contexto estático (`application='AccioHub'`).
- **Escopo Delimitado:** Esta recomendação não antecipa nenhuma decisão sobre P1.3 ou remoção do contrato; ela preserva intacto todo o arcabouço de segurança e integridade construído na P1.2F.
