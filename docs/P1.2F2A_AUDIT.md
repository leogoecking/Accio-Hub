## 4. Auditoria da Política de URLs e Matriz de 114 Casos

### 4.1 Segurança da Expressão Regular e Normalização
O analisador de segurança [`SafeReferenceUrl`](file:///home/goecking/Projects/Accio-HUB/rails/app/services/safe_reference_url.rb) divide a validação em três estágios estritos:
1. **Esquema e Estrutura RFC 3986:** Valida a presença obrigatória de `http` ou `https` em minúsculas ou maiúsculas, com barras `//` e sem caracteres de controle (`\r`, `\n`, `\t` ou `\0`).
2. **Autoridade Explícita (`AUTHORITY_PATTERN`):** A expressão regular `\A(?<host>(?:\[[a-fA-F0-9:.]+\]|[^:/?#@]+))(?::(?<port>\d{1,5}))?\z` garante que:
   - Não existam credenciais com `@` em nenhuma posição da autoridade.
   - Não haja percent-encoding (`%20`, `%40`, etc.) no host ou autoridade.
   - Não seja permitida porta vazia (e.g. `https://example.test:`).
   - Portas numéricas estejam estritamente entre 1 e 65535.
3. **Resolução de Ambiguidade Numérica (Alinhamento WHATWG):**
   - O padrão WHATWG de navegadores tenta interpretar qualquer endereço cujo último rótulo seja puramente numérico ou hexadecimal como um endereço IPv4 (admitindo formatos hexadecimais, octais e inteiros puros). Isso poderia levar o navegador a converter `https://0x7f000001` em `https://127.0.0.1`, enquanto um backend Rails permissivo o trataria como um nome de domínio arbitrário.
   - A heurística do Accio Hub inspeciona o host: se o host contiver formato hexadecimal ou terminar com um rótulo numérico, ele **exige estritamente** o formato IPv4 decimal canônico com quatro octetos de 0 a 255.
   - Caso não atenda a esse formato exato, o endereço é rejeitado como ambíguo.

### 4.2 Resultados da Matriz de 114 URLs Sintéticas
A auditoria reexecutou a matriz comparativa completa entre o serviço Ruby e o parser WHATWG do Chromium (`new URL()` e elemento de âncora isolado em `about:blank`), com zero tráfego de rede (`rails/script/reference-url-matrix.mjs`):
- **Total de casos sintéticos avaliados:** 114.

- **Rejeitados pela política do Accio Hub:** 84.

- **Requisições de rede externas:** Exatamente 0 (nenhuma chamada de DNS, handshake TLS ou requisição HTTP foi emitida).

### 4.3 Breaking Changes Legítimas (Comparação com a P1.2D3)
Em relação à política implementada anteriormente na P1.2D3, exatamente **15 padrões sintéticos de URL** que eram aceitos de forma permissiva passaram a ser rejeitados para novas criações ou edições:
1. Endereços numéricos hexadecimais (e.g. `https://0x7f000001/a`).
2. Endereços numéricos octais (e.g. `http://0177.0.0.1`).
3. Endereços com inteiros puros (e.g. `http://2130706433`).
4. Endereços IPv4 abreviados com 2 ou 3 partes (e.g. `http://127.1`).
5. Portas vazias com dois-pontos soltos (e.g. `https://example.test:`).
6. Nomes de domínio cujo rótulo final é puramente numérico ou ambíguo (e.g. `https://example.123/path`).

A auditoria confirma que essa restrição é tecnicamente fundamentada, necessária para a robustez do produto e não causa perda de dados para registros pré-existentes.

## 5. Preservação de Dados e Tratamento de Legados

### 5.1 Apresentação Segura sem Executabilidade
Registros legados pré-existentes no SQLite que possuam URLs incompatíveis com o novo hardening (como `https://0x7f000001/legacy` ou tentativas de injeção como `https://example.123/<img src=x onerror=alert(1)>`) são protegidos:
- **Ausência de Âncora:** A view `_list.html.erb` verifica `ProjectsHelper.safe_reference_url(reference.url)`. Para URLs incompatíveis, o retorno é `nil`.
- **Texto Puro Escapado:** O valor original é renderizado como texto puro escapado pelo ERB dentro de `<p class="muted" data-reference-url-incompatible><%= reference.url %></p>`.
- **Zero Tags ou Scripts:** A verificação em navegador confirmou que `document.querySelectorAll(".space-reference img, .space-reference script")` retorna 0 elementos.
- **Zero Atributos `href`:** Não há nenhum atributo `href` navegável associado à URL incompatível.

### 5.2 Edição e Reparo Explícito
No fluxo de edição de uma referência legada:
1. O formulário abre preservando a string original no campo `<input type="url" id="reference-url">` para permitir ao usuário visualizar e corrigir o endereço.
2. Caso o usuário tente salvar o formulário sem alterar a URL inválida, o backend rejeita com **HTTP 422 Unprocessable Content**. O modal permanece aberto, exibe mensagem instrutiva em `data-project-notice` e nenhum dado é gravado no banco de dados.
3. Quando o usuário digita uma URL válida e submete o formulário, a alteração é aceita com HTTP 200, a **UID original é preservada**, o `lock_version` é incrementado e a referência passa a ser exibida como link navegável com `data-reference-url-incompatible` removido.

### 5.3 Isolamento em Projetos Arquivados
Em projetos com status `archived`:
- As referências legadas continuam visíveis como texto puro para fins de documentação.
- O botão de edição e o botão de nova referência são suprimidos (`data-reference-opener` ausente).
- Requisições diretas de edição via comando são bloqueadas pelos gatilhos SQL e pelos controllers.
- A restauração do projeto (`restore`) restabelece os controles de edição com segurança.
